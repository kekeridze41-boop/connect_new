# Connect

## Назначение и границы проекта

Connect — консольная утилита для подключения к сетевому оборудованию по SSH или Telnet, автоматической диагностики ONU/ONT и последующей ручной работы в CLI устройства. Целевая платформа — Debian/Ubuntu. Распространение предусмотрено через Debian-пакет и подписанный APT-репозиторий на GitHub Pages.

Документ составлен по текущим исходникам, README.md, AGENTS.md, workflow публикации и доступной истории текущей сессии. Описанные возможности отражают реализацию; испытания на оборудовании в этой сессии не проводились. В сессии не зафиксированы дополнительные архитектурные решения помимо требования вести этот документ и поддерживать его актуальность.

## Архитектура

| Файл | Ответственность |
| --- | --- |
| `connect.sh` | Основной скрипт Tcl/Expect: аргументы, загрузка конфигурации, выбор устройства и подключения, авторизация, диагностика, интерактивная сессия. Расширение `.sh` не означает Bash. |

| `packaging/build.sh` | Сборка пакета `connect` архитектуры `all`, размещение скриптов и создание исполняемой обёртки. |
| `.github/workflows/publish.yml` | Сборка пакета, подготовка и подпись индексов APT, публикация на GitHub Pages. |

| `README.md` | Пользовательская инструкция установки, использования и обновления. |

Логика оборудования сосредоточена в `connect.sh`: отдельных драйверов, внешней базы оборудования и автоматических тестов в текущем проекте нет.

## Интерфейс и последовательность работы

- `connect IP [PORT]` подключается к устройству; необязательный `PORT` обозначает порт/ONU оборудования, а не TCP-порт подключения.
- `connect --setup` запускает настройку учётных данных через установленную обёртку.
- При отсутствии IP скрипт выводит подсказку и завершает работу. При отсутствии конфигурации выводит ошибку.
- Конфигурация загружается через Tcl `source`. По спискам IP выбираются протокол, учётная запись и тип устройства; если IP не найден, тип определяется по формату порта.
- По умолчанию используются Telnet и личная учётная запись. Для списка ZTE C610 используется SSH с личной учётной записью; для списка C-DATA — SSH с административной. Для одного устройства C-DATA предусмотрен отдельный пароль. Eltex MA4000 из списка использует Telnet с административной учётной записью.
- Распознавание типа по формату порта не меняет протокол и учётную запись.
- Для ZTE C320/C610 выполняется переход в `enable`, если приглашение ещё не привилегированное. Для C-DATA предусмотрены переходы в `enable` и `config`.
- Если передан порт, проверяется его формат и выполняются настроенные команды диагностики. После этого вызывается `interact` для ручной работы. Без порта диагностика пропускается, но переходы в режимы CLI сохраняются для определённых по IP устройств.

## Поддерживаемое оборудование

| Тип | Определение | Формат порта | Реализованная диагностика |
| --- | --- | --- | --- |
| ZTE C610 | Список IP | `карта/слот/ветка:ONU` | Состояние ONU, Ethernet, MAC через vport, оптическое затухание. |
| ZTE C320 | Формат порта | `карта/слот/ветка:ONU` | Состояние ONU, Ethernet, оптическое затухание, MAC. |
| C-DATA | Список IP или формат порта | `0/слот/ветка/ONU` | Состояние ONU, оптические параметры, состояние всех Ethernet-портов. |
| Eltex MA4000 | Список IP | `слот/ветка/ONU` | Состояние ONT, порты, MAC. |
| Eltex MES | Формат порта | `faN/N/N` или `giN/N/N`, без учёта регистра | Только распознавание; диагностика не настроена. |
| SNR | Формат порта | `N/N/N` | Только распознавание; диагностика не настроена. |
| Eltex LTP | Формат порта | `N/N` | Только распознавание; диагностика не настроена. |
| Zyxel | Формат порта | `N` | Только распознавание; диагностика не настроена. |

Здесь `N` обозначает последовательность цифр. Для C-DATA распознавание допускает четыре числовых компонента, но последующая проверка требует начальный `0`. Приоритет списков IP позволяет отличать MA4000 от SNR при одинаковом формате порта.

## Реализованные функции и технические решения

### Подключение и диагностика

Expect автоматизирует диалог с SSH/Telnet и передаёт тот же сеанс пользователю. Общий тайм-аут ожидания — 20 секунд. Скрипт обрабатывает запросы логина и пароля, приглашения с окончанием `>` или `#`, ряд ошибок авторизации, тайм-ауты и закрытие соединения.

Команды диагностики заданы последовательными списками для каждого типа. Для C-DATA перед запросами выбирается интерфейс GPON. Для C320 имя ONU формируется с префиксом `gpon-onu_`, для C610 — с `gpon_onu-`; MAC на C610 запрашивается через vport с преобразованием `карта/слот/ветка:ONU` в `карта/слот/ветка.ONU:1`. Эти различия реализованы явно в основном скрипте.

Постраничный вывод с маркерами `--More--` и `---- More ----` продолжается отправкой пробела. Вывод CLI показывается пользователю; отдельного разбора результатов диагностики, отчётов или хранения истории не реализовано.

Перед каждой командой диагностики OLT выводится русское пояснение её назначения, затем текст команды. Пояснения хранятся отдельными списками в том же порядке, что и команды. После получения приглашения CLI выполняется пауза 3 секунды для чтения результата, включая последнюю команду перед переходом в интерактивный режим. Пауза не применяется при тайм-ауте или закрытии соединения; тексты и порядок диагностических команд сохранены.

### Проверка порта коммутатора

При переданном порте для типов `eltex_mes`, `snr` и `unknown` после авторизации выполняется `show interface status`. Скрипт собирает вывод с обработкой постраничной выдачи и извлекает из первого столбца имена вида `gi1/0/1`, `fa1/0/1`, `g0/2` и другие с буквенным префиксом и числовыми компонентами через `/`. Проверяется наличие порта в таблице без учёта регистра; сохраняется обозначение из ответа устройства. Таблица не служит достоверным определением производителя или модели: исходное определение типа по аргументу сохраняется.

Если порт не найден, оператор видит примеры из таблицы и может повторить ввод. Пустая строка или конец локального ввода отменяют выбор и передают управление в `interact`. При тайм-ауте или отсутствии распознанных интерфейсов проверка прекращается с сообщением и переходом в `interact`. Для OLT существующие проверки и диагностические команды сохранены. Устройства SNR с иным синтаксисом команды или таблицы могут не поддерживать эту проверку; отдельного запроса для SNR пока нет. Формат таблиц различных прошивок MES требует проверки на реальных примерах; испытания на оборудовании не проводились.

### Конфигурация

Учётные данные хранятся в `~/.config/connect/credentials.conf`: каталог имеет права `700`, файл — `600`. Настройка запрашивает личную и административную учётные записи и отдельный пароль для специального устройства; пароль вводится без отображения. Перезапись существующего файла требует подтверждения.

Встроенный Python кодирует символы значений Unicode-последовательностями для Tcl и записывает присваивания. Используются `umask 077` и явное ограничение прав. Конфигурация является исполняемым Tcl-кодом, а не пассивным форматом данных. Пакет не включает пользовательскую конфигурацию; установщик сохраняет существующий файл. `.gitignore` исключает `credentials.conf`, некоторые файлы секретов и результаты сборки.

### Установка и распространение

Пакет устанавливает скрипты в `/usr/share/connect/` и обёртку `/usr/bin/connect`. Обёртка передаёт обычные аргументы `/usr/bin/expect`, а `--setup` направляет в настройку. Зависимости пакета: `expect`, `openssh-client`, `inetutils-telnet`, `python3`.

Установщик требует обычного пользователя, APT и sudo; устанавливает необходимые средства загрузки и проверки ключа. Загруженный публичный ключ сверяется с закреплённым в установщике отпечатком, устанавливается в `/etc/apt/keyrings/`, источник APT использует `signed-by`. Обновления выполняются стандартными средствами APT.

Workflow запускается по тегам `v*.*.*` или вручную. Версия берётся из имени Git-ссылки с удалением начального `v` и проверяется как три числовых компонента. Формируются `Packages`, `Packages.gz`, `Release`, `InRelease` и `Release.gpg`. Приватный ключ и пароль подписи передаются через GitHub Secrets. Публикация выполняется отдельным заданием GitHub Pages.

## Известные проблемы и ограничения

Ниже перечислены наблюдения по исходникам; они не означают, что исправления уже согласованы.

- Пароль `enable` ZTE задан непосредственно в `connect.sh`. Его значение здесь намеренно не приводится; изменение хранения требует отдельного согласования.
- SSH отключает проверку и сохранение ключей узлов и разрешает ряд устаревших алгоритмов. Это текущее поведение подключения; причина выбора в доступной сессии не зафиксирована. Telnet не шифрует передаваемые данные.
- Рекомендованная в README установка через `curl ... | bash` использует стандартный ввод для текста скрипта, а настройка читает ответы через `read` из стандартного ввода без явного обращения к терминалу. Это создаёт проблему интерактивной первоначальной настройки при таком запуске; воспроизведение установки в этой сессии не выполнялось.
- Ручной запуск workflow с обычной ветки не пройдёт проверку версии, если имя ссылки не соответствует ожидаемой версии. Отдельного параметра версии для ручного запуска нет.
- Для MES, SNR, LTP и Zyxel отсутствуют команды автоматической диагностики.
- Списки оборудования встроены в код; определения по порту недостаточно для выбора SSH и административной учётной записи. Формат проверяется регулярными выражениями без проверки допустимых диапазонов слотов и ONU.
- Ожидание CLI основано на общих шаблонах приглашений; ответы диагностических команд не проверяются на ошибки устройства. После тайм-аута возможен вывод сообщения о завершении диагностики, поэтому это сообщение само по себе не подтверждает успешность всех команд.
- Загрузка конфигурации через `source` предполагает доверие к её содержимому; отдельной проверки обязательных полей перед использованием нет.
- Автоматических тестов нет. Совместимость с конкретными версиями прошивок и работа релизного процесса в текущей сессии не проверялись.

## Незавершённые задачи

Явно видимая в коде незавершённая функциональность — диагностика Eltex MES, SNR, Eltex LTP и Zyxel. Конкретные команды для неё в проекте не определены.

### План развития диагностики коммутаторов

Пользователь обозначил следующую последовательность работ:

1. Реализовать проверку формата порта коммутатора: для Eltex MES — формат вида `fa1/0/1`, для SNR — `1/0/1`.
2. После реализации проверки добавить диагностические команды, выбираемые в зависимости от определённого типа коммутатора — Eltex MES или SNR.

Распознавание этих типов по формату порта есть; добавлена проверка по таблице `show interface status` после подключения с повторным вводом и отменой. Диагностических команд для выбранного порта пока нет. Текущий код также распознаёт префикс `gi` для Eltex MES; его поддержка в будущей проверке отдельно не уточнена. Конкретные диагностические команды и допустимые диапазоны компонентов порта пока не определены.

Это план будущих изменений; в рамках его записи исходный код не менялся. Сроки и отдельный план исправления остальных ограничений в доступной сессии не определены. Изменения подключения, авторизации, диагностики и хранения секретов требуют согласования согласно `AGENTS.md`.
